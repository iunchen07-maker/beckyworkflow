# SPEC 章節編號規則

> **設計目標：**
> 1. **編號穩定** — 新增 US- 不會引起後面整批重編號
> 2. **可引用** — PM 拿到一個編號能 5 秒內 jump 到正確章節
> 3. **可遵守** — Spec-writer 不需要全文掃描就知道下一個編號是什麼
> 4. **可預防** — 寫入流程內建編號完整性檢查，避免再次出現重複編號

---

## 一、為什麼採用這套規則

典型踩雷模式（示意）：
- §US-A1.1 和 §US-B1.1 都被編成 `3.1.1`（編號碰撞）
- 同一 Chapter 內「純章節編號」與「US- 標題」混排，格式不一致

根因：若把「章節編號」與「US- 標題」綁定（US-A1.1 → 3.1.x），但 US- 標籤系統有獨立邏輯（字母前綴對應功能子分區），兩個系統互不對應，就會造成編號碰撞。

**新規則的核心做法：把「章節編號」與「US- 內部編號」分開**。Chapter 編號只用於大區分類；US- 內部子節編號自己連續、跟其他 US- 完全獨立。

## 二、層級結構

| 層級 | Markdown | 用途 | 例子 |
|---|---|---|---|
| H1 | `# <N>. <章節名>` | Chapter 大區（按業務階段分） | `# 2. 清單管理（建立 + 分享）` |
| H2 (US) | `## US-<id> <標題>` | 一個 user story | `## US-L1.1 建立清單` |
| H2 (附錄) | `## 附錄 <X>: <名稱>` | SPEC-wide 共用內容 | `## 附錄 A: 狀態值對照表` |
| H3 (子節) | `### US-<id>.<seq> <標題>` | US- 內部章節 | `### US-L1.1.7 驗收條件` |
| H3 (附錄子節) | `### <X>.<seq> <標題>` | 附錄子節 | `### A.1 任務狀態` |
| H4+ | `#### ...` / `##### ...` | 子節內細部分段（不參與編號） | `#### 範例` / `##### 邊界` |

**禁止使用：**
- ❌ H2 「純 Chapter 編號 + 文字」（如 `## 5.2 提醒規則補充`）— 必須掛在某個 US- 下，或升級為獨立 US-
- ❌ H3 「純 Chapter 編號」（如 `### 4.1.1 模組概述` 不附 US- 前綴）— 必須帶 US- prefix
- ❌ H2 同時帶 Chapter 編號和 US- 標題（如 `## 5.4 US-T5.3 任務批次封存`）— 二擇一，永遠用 US- 標題

### 特例：Metadata 章節（僅 Chapter 1 適用）

**適用條件**（三項必須**全部**符合，否則不適用本特例）：
1. 章節為**文件 metadata 性質**，內容類型限：
   - 文件涵蓋範圍 / 版本說明 / 作者署名
   - Glossary 對齊段（在文件內提示讀者去查 Glossary，或在 SPEC 內列簡表）
   - 流程總覽 / Phase 對照圖
   - Navigation 結構 / 頁面路徑對照表
   - 其他「描述文件本身或文件與系統脈絡對應」的內容
2. **不含任何業務 user story 的功能規格**（功能、欄位、互動、驗收條件、UI 規則等）
3. **僅限 Chapter 1**（文件說明）

**允許格式：**

| 層級 | Markdown | 例子 |
|---|---|---|
| H2 | `## <N>.<X> <名稱>` | `## 1.4 Navigation 結構` |
| H3 | `### <N>.<X>.<Y> <名稱>` | `### 1.4.1 My Lists` |

**引用語法：** `§<N>.<X>` 或 `§<N>.<X>.<Y>`（例：`§1.4` / `§1.4.1`）

**禁止事項：**
- ❌ 其他 Chapter（2、3、4、5、6、7 等業務章節）援引此特例 — 它們必須遵守一般 H2 US- / H3 US- prefix 規則
- ❌ Chapter 1 內出現業務 user story 規格（若有，須抽出為獨立 US- 並移至對應業務 Chapter）
- ❌ Spec-writer 自行判斷某段「看起來像 metadata」就套用此特例 — 必須符合上述三項適用條件

**Spec-writer 寫入時的判斷流程：**
1. 要新增的章節是否屬於 Chapter 1？→ 否，套一般規則；是，繼續
2. 內容是否完全符合 metadata 性質（不含任何功能規格）？→ 否，須移至對應業務 Chapter 並套一般規則；是，繼續
3. 套用本特例的 H2/H3 編號格式

## 三、編號約定

### 3.1 H1 Chapter 編號

- 從 `1` 開始連續編：`# 1. 文件說明`、`# 2. 清單管理`、`# 3. ...`
- Chapter 編號 **只出現在 H1**，不滲透到 H2/H3
- 新增 Chapter 一律在最後追加（取現有最大 Chapter 號 + 1）；不插入、不重編既有 Chapter（§3.5「既有編號永不重編」）

### 3.2 H2 US- 標題

- 格式：`## US-<id> <人類可讀標題>`
- `<id>` 沿用既有命名慣例（如 L1.1、L1.2、T1.1、T2.1、U1.2 等：字母前綴＋分區序號）
- 同一個 `<id>` 在整份 SPEC 內只能出現一次
- US- 標題之間**不需要連續或對齊 Chapter 編號**（US- 標籤系統獨立；退役號留空不重用），但**實體排列必須依 id 遞增**（見 §3.5）
- 新增 US- 依 §3.5 取號（依實體落點取號，不會引起其他 US- 重編號）

### 3.3 H3 US- 內部子節

- 格式：`### US-<id>.<seq> <標題>`
- `<seq>` 從 `1` 開始連續編，**僅在該 US- 內部**遞增
- 不同 US- 的 `<seq>` 完全獨立（US-L1.1.7 跟 US-T1.1.7 互不相干）
- 邊界規則、附註等子節，視為一般 H3 接續編號（不另開特殊號段）；新子節一律取該 US- 的 max+1
- **決策史不進 SPEC**：不新開「拍板紀錄」子節／附錄／時間軸、不往既有的拍板紀錄段追加；決策史寫進專案 `Spec/memory/` 決策檔（`phase-0-spec-update.md` §SPEC 生命週期 3）。既有 SPEC 殘留的拍板紀錄段由各專案開專項清理，日常寫入不動它

### 3.4 附錄編號

- H2：`## 附錄 A: 狀態值對照表`（A、B、C ... 連續）
- H3：`### A.1 任務狀態`（A.1、A.2 ... 在該附錄內連續）
- 附錄只放 SPEC-wide 共用的現行內容（對照表、共用規則），不放拍板紀錄（見 §3.3）
- 附錄編號獨立於 Chapter / US-，永不與正文編號衝突

### 3.5 實體排列順序與保留編號

**排列順序（標題層鐵則）：**

- 全檔 H2 `US-<id>` 的**實體排列必須依 id 遞增**（一條線讀到底，不分 Chapter 重算）；H3 `<seq>` 在該 US- 內同樣實體遞增。目的＝拿到編號 5 秒 jump 到位。
- **取號時機＝寫入正本當下、依實體落點取號**（新 US- ＝落點前一個 US- 的 id 之後；通常＝全檔 max+1 放檔尾語意所屬 Chapter）。**討論稿／工作稿的臨時序號（討論順序編號、題號、候選編號）不得直接沿用為正本節號**——順序錯亂的根因就是把「討論順序」帶進「語意排列」的文件。
- 新節語意上屬於**前面的 Chapter**、但落點前後兩個 id 之間沒有可用的號（或 Chapter 語意分組與 id 順序打架）時 → **不重編既有節、不硬塞成非遞增排列**：新節取全檔 max+1 放檔尾，回報 PM 列為已知排列債務。
- **散文目錄類清單**（表格列、粗體條列的目錄項，如以字母前綴流水編號的項目清單）＝**依語意分組排列、編號只當錨點**，不吃標題層遞增鐵則；**退役號（落選候選／收掉項）不重用**，新項一律取該系列 max+1。
- **`Spec/Deferred/*.md` 檔頭 `保留編號：` 列的號視同已存在**（US- 與目錄號皆然）：取號查重、算 max+1 都要連 Deferred 一起算。
- **既有編號永不重編**（H2／H3／目錄列皆然）：刪除或退役的節**保留 heading 行（目錄類保留該列）**，下一行（或該列內容欄）註記「已退役（保留編號）」；搬去 Deferred 的 heading 改成 `<編號> <功能名> — 已移至 Deferred/<功能>.md（保留編號）`（不留延後字樣、議題、日期；目錄類該列內容欄寫「已移至 Deferred/<功能>.md（保留編號）」）。佔位 heading 照算 `<seq>`，所以不會出現跳號；不刪、不重用。新增節的取號方式不變。

**執法強度**：排列順序的違規＝**列入回報給 PM，不擋寫入、不由 agent 自動搬動整節**（搬節非機械性修正）；編號連續／不重複維持既有硬檢查。既有 SPEC 的歷史違規＝各專案開專項議題清理，不在日常寫入時順手動。

## 四、引用語法

| 引用對象 | 寫法 | 例子 |
|---|---|---|
| 同檔內 US- 整體 | `§US-<id>` | `§US-L1.1` |
| 同檔內 H3 子節 | `§US-<id>.<seq>` | `§US-L1.1.7` |
| 同檔內附錄 | `§附錄 <X>` 或 `§附錄 <X>.<seq>` | `§附錄 A.1` |
| 跨檔（推薦完整路徑） | `<檔名> §US-<id>.<seq>` | `Spec/Tasks/02_任務管理.md §US-T1.1.7`（source md 固定檔名、不押日期） |
| Chapter 整體 | `Chapter <N>` 或 `§<N>` | `Chapter 2` / `§3` |

**禁止寫法：**
- ❌ 同時混用 `§4.0.7` 與 `§US-L1.1.7` 指同一處 — 統一用 US- 編號
- ❌ 寫 `§US-L1.1 §7` —（去掉中間的空格與小節符號）統一用 `§US-L1.1.7`
- ❌ 寫 `§US-L1.1 §模組概述` —（用 seq 編號而非標題文字）

## 五、Spec-writer 強制檢查清單

**寫入前（必執行）：**

1. 用 `Grep` 抽取目標 SPEC 的所有 H1/H2/H3 標題行
   ```
   pattern: ^#+ .+
   ```
2. 確認本次要新增的 H3 子節 `<seq>` = 該 US- 現有最大 `<seq>` + 1（含保留編號佔位）
3. 確認本次要新增的 US- `<id>` 在整份 SPEC 中不存在、也不在 `Spec/Deferred/` 保留編號；**取號依實體落點（§3.5），不沿用討論稿臨時序號**
4. **若發現既有編號衝突或格式違規** → **停止寫入**，在回報中明示違規清單給 PM 處理（不要自行修補）

**寫入後（必執行）：**

1. 再次 Grep 抽取所有 H1/H2/H3 標題
2. 驗證：
   - [ ] H2 全部符合 `## US-<id>` 或 `## 附錄` 或 `# <N>.` 之一
   - [ ] 沒有 H2 同時帶 Chapter 編號與 US- 標題（如 `## 5.4 US-T5.3`）
   - [ ] H3 全部符合 `### US-<id>.<seq>` 或 `### <附錄 letter>.<seq>` 之一
   - [ ] 同一個 US- `<id>` 沒有重複
   - [ ] 每個 US- 的 H3 `<seq>` 在該 US- 內連續（1, 2, 3, ...，無跳號、無重複；保留編號佔位 heading 算在內，跳號＝佔位被刪 → 還原佔位，不重編）
   - [ ] **H2 US- 實體排列依 id 遞增、H3 `<seq>` 實體排列遞增（§3.5）**
   - [ ] 本次沒有新增拍板紀錄子節／附錄／條目（§3.3）
3. 若驗證失敗 → 修正後重新驗證；驗證通過才能宣告寫入完成（**排列順序類違規若源自既有結構、非本次寫入造成 → 依 §3.5 執法強度回報 PM，不自行搬節**）

**Self-Review 對照表必須附上：**
```
**章節編號完整性檢查：**
- [x] 本次新增 US- id 確認唯一
- [x] 本次新增 H3 seq 與該 US- 既有 seq 連續
- [x] 寫入後全檔 H2/H3 grep 結果無重複、無跳號、無格式違規
```

## 六、Impact-scanner 強制檢查清單

掃描定案草案影響範圍時：

1. 除了「定案草案 vs 既有條文」的衝突檢查外，**順便對目標 SPEC 跑章節編號完整性掃描**
2. 若發現既有編號破損（重複、跳號、格式違規、**實體排列非遞增**——定義見 §3.5），列入掃描報告的「**【既有編號問題】補充提示**」段（不算強連動，但要讓 PM 知道）
3. 提示格式：
   ```
   ### 【既有編號問題】補充提示
   - 檔案：<path>
   - 問題：§US-A1.1 與 §US-B1.1 都被編成 3.1.1
   - 建議：回報 PM，記為已知債務（不重編既有編號，見 §3.5／§七）
   ```

## 七、既有 SPEC 不做重編號遷移

- 本規則不回溯重編既有 SPEC；既有的 US- 號、H3 `<seq>`、附錄號、目錄號一律原樣保留（§3.5）。
- 舊格式殘留（重複號、純 Chapter 編號的 H2/H3、排列非遞增）照 §3.5 執法強度回報 PM，由各專案開專項議題處理。專項把無 US- 前綴的舊段落轉成 US-／附錄格式時，新 id 依 §3.5 取號（空號或 max+1），已有的 US-／附錄號不動；指向舊段落的 Chapter 式引用（如 `§4.1.1`）在同一專項內改成新引用。

## 八、好例子 vs 壞例子

最小對照一組（各違規類型 §二已逐條定義，不在此重複枚舉）：

### ✅ 正確

```markdown
# 2. 清單管理（建立 + 分享）

## US-L1.1 建立清單

### US-L1.1.1 模組概述      ← H3 帶 US- prefix，seq 在該 US- 內連續
```

### ❌ 錯誤

```markdown
# 4. 任務提醒

## 4.1 任務到期提醒      ← ❌ H2 是 Chapter 編號，不是 US- 標題

### 4.1.1 模組概述         ← ❌ H3 沒帶 US- prefix，會與他節撞號
```

## 九、規則演進

修改規則需：

1. 在本文件末「變更紀錄」節記錄變更日期 + Why
2. 更新 `phase-0-spec-update.md` 與 `phase-0-impact-scan.md` 對應段落
3. 新規則不回溯重編既有 SPEC（§七）

任何 agent / PM 發現本規則無法覆蓋的編號情境，**先停止寫入**並回報 PM 補規則，不要自行延伸。
