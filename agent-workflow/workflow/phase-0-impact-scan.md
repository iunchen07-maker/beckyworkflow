# Phase 0｜影響範圍掃描（拍板前防護網）

> **角色定位：** 在 PM 做最終拍板之前，由 Opus subagent 掃描整份 SPEC，回報「本次定案草案會與哪些既有條文衝突或連動」。
>
> **不是寫入 agent**：scanner 不改任何檔案、不寫修改文字、不替 PM 做選擇。它只負責**指出問題**。

---

## 為什麼需要這層

PM ↔ Opus 討論時注意力集中在本次議題，容易漏掉跨章節 / 跨議題連動；漏掉的連動讓 spec-writer 寫入時中斷，或讓 SPEC 條文互相矛盾。Scanner 在「定案草案出來、PM 拍板前」執行，把連動風險納入拍板素材。

---

## 在 Phase 0 內的位置

Scanner 是 ④（完整步驟編號與執行順序以 `phase-0-spec-update.md` 為準）。它的存在讓 ⑥ 拍板的資訊更完整。

---

## 掃描範圍（SPEC source of truth＝md）

### ✅ 必掃

| 範圍 | 為什麼 |
|---|---|
| `Spec/` 下所有 **.md** | 個案規格（拆檔 `<module>/NN_*.md` source of truth，就地 Edit、不押日期）+ 架構脈絡（Project_Context）+ 決策原則（Decision_Principles）+ Glossary + Permission Matrix + README |
| `Spec/Deferred/*.md`、`Spec/BACKLOG.md` | 延後功能＋接回清單；**不是現行規則、不判衝突**，只做下方§接回錨點 |
| `討論排程/` 下**已定案**議題（標題含「✅ 定案」或檔名後綴 `_定案`、或內容明示「狀態：已定案」） | 已拍板的決議是事實層 |
| 專案資料夾根目錄背景文件（依該專案 CLAUDE.md「必讀背景文件」清單所列的 .md） | 功能規格主檔 / 狀態機定義 / 系統脈絡等，依專案而定 |

### ❌ 絕對不掃

| 範圍 | 理由 |
|---|---|
| `Spec/` 下所有 **.docx** | **docx 為 rendered output / 封存版**（CLAUDE.md 明示：歷史 docx 不再追加修改，僅供人工翻閱）。source of truth 是同名 .md，掃 docx 會重複讀內容、且舊版 docx 還可能讀到已過時文字污染結果 |
| 任何名稱含 `History` 的資料夾 | CLAUDE.md 紅線，舊版污染區 |
| mockup 封存資料夾 | 同上 |
| `HTML設計稿/` | mockup 是 Phase 1 產出物，文字定稿後再處理 |
| `討論排程/` 下**未定案**的議題 | 尚未拍板，不算事實層，掃了會誤判 |

### ⚠️ 條件掃

| 範圍 | 條件 |
|---|---|
| UI 元件庫 reference（若專案有） | 預設不掃；若 PM 在輸入中明示「本次決策涉及 UI 元件選用」才掃 |

## 輸入格式（從 Opus 接收）

Opus 呼叫 scanner 時，必須提供以下**結構化清單**：

```markdown
## 議題編號與標題
議題 N — <標題>

## 本次定案草案（一條決策一行）
1. 對 <X> 採取 <Y> 規則
2. 對 <A> 改為 <B>
3. 排除 <Z> 不在本議題範圍
...

## 草案中改動既有規格的點（已知）
- 議題 M 子題 X 的「<原規則>」改為「<新規則>」（Opus 自己已抓到的連動）
- ...

## 重點關鍵詞（協助 scanner 篩選相關章節）
負責人、指派、成員、協作者、多人...
```

> Scanner **不負責從討論文字推敲草案**。如果 Opus 沒整理清楚就丟過來，scanner 應該拒絕執行並回報「輸入格式不完整」。

---

## 輸出格式（三層分類）

報告依序五段：**【強連動】必須一起改 → 【弱連動】請 PM 確認是否連帶調整 → 【無影響】已掃描無衝突 → 掃描範圍宣告 → 【既有編號問題】補充提示**（末段＝對目標 SPEC 順掃章節編號完整性，照 [`SPEC_NUMBERING_RULES.md`](./SPEC_NUMBERING_RULES.md) §六；破損不算強 / 弱連動，是給 PM 的補充提示，附「本次拍板是否涉及」；既有編號不重編，破損記為已知債務）。

**每項必含欄位：**

- **強連動**：檔案＋章節 / 原文摘要 / 衝突點 / 建議處理方向（方向而已，不寫具體修改文字）
- **弱連動**：檔案＋章節 / 原文摘要 / 關聯點 / PM 判斷選項（A / B / C）
- **無影響**：已掃描的檔案清單，每檔一句「為何無關」
- **掃描範圍宣告**：✅ 已掃 / ⏭️ 跳過 / ⏱️ 掃描檔案總數
- **既有編號問題**：檔案 / 問題（重複、跳號、格式違規）/ 建議

### 三層分類定義（避免 scanner 亂分）

| 層級 | 判定標準 | 例子 |
|---|---|---|
| **強連動** | 既有條文文字明確被本次決策推翻、改寫，否則會造成 SPEC 內部互相矛盾 | 既有「任務可指派給多位成員」 vs 草案「每個任務只能有一位負責人」 |
| **弱連動** | 既有條文與本次決策共用同一概念或關鍵詞，但保留現狀也不會矛盾，只是可能不一致 | 任務卡片上負責人頭像的排列方式 |
| **無影響** | 已檢查過，主題不重疊或關聯點極弱 | Glossary 中無相關名詞、不同模組的章節 |

## crosscheck 八面向（與三層分類並行）

掃連動時，除了「草案 vs 既有條文衝突」，順著八個面向系統性比對草案與既有 SPEC 是否一致；不一致者歸入對應連動層（衝突→強連動、相關未矛盾→弱連動）：

| 面向 | 比對對象 |
|---|---|
| 術語一致 | Glossary 正式名詞 / 禁用名詞 |
| API 規範 | 共用 API 端點 / 欄位 / 錯誤碼（若 SPEC 有） |
| 權限邏輯 | Permission Matrix / 角色操作權限 |
| 狀態機邏輯 | 既有狀態值 / 轉換條件 |
| 跨 SPEC 引用 | 其他 US- 對同功能的描述有無矛盾 |
| **彙總層同步** | **彙總檔的敘述欄是否還在描述被本次覆蓋掉的舊行為**（見下方§彙總層反查） |
| 同列／同表全列重讀 | 關鍵詞命中表格某一列時，整列所有欄位與同表其他列是否還在描述舊行為 |
| 死路檢查 | 草案封鎖某階段／狀態／權限後，受影響的每張卡、每個按鈕的清除動作（完成／撤銷／關閉／刪除）還做得到嗎 |

八面向是**掃描的 lens**，不另開報告段；命中者寫進既有的強 / 弱連動清單。

---

## 彙總層反查（US-ID 反查，非關鍵詞比對）

**彙總層 ＝ 自身不是規則權威、內容全部從別的 US 段推導出來的檔**（典型：通知清單、狀態總表、權限總表）。這種檔會標明「規則的 source of truth 在各 US 段，本檔為摘要」，因此**規則一被覆蓋，它的敘述欄就會默默過期**——而且過期的是彙總檔（如通知清單）各敘述欄這類自由措辭，**關鍵詞比對抓不到**（措辭早就跟原 US 長得不一樣了）。

**掃法（機械、不吃措辭）：**

1. 從專案 `CLAUDE.md` 讀「彙總層檔案」宣告（沒宣告 → 此面向跳過，並在報告末尾註明）。
2. 取本次草案改動的每個 **US-ID**。
3. 在彙總檔中反查：**哪幾列的「對應功能（US）」欄含這個 US-ID** → 那幾列**整列**（彙總檔的各敘述欄，全部欄位）列入必審。
4. 逐列比對敘述是否仍成立，不成立者歸強連動。

> **為什麼用 ID 不用關鍵詞**：典型失敗模式是「規則本體改對了，彙總檔的敘述欄還在描述舊行為，之後有人憑舊口徑做決定」。ID 是穩定鍵、措辭不是。

**寫入後還有第二道**：`@phase0-spec-verifier` 維度 1 對「本批新增／修改的彙總層列」重讀其「對應功能（US）」欄引用的每個 US 段，確認觸發條件與權威段無矛盾。兩道一前一後，前者防覆蓋時漏改、後者防寫入時抄錯。

---

## 接回錨點（`Spec/Deferred/`）

延後功能靠接回清單的**錨點**（活檔裡逐字存在的剪後句／保留的佔位 heading 或前一節 heading）接回；草案改寫了錨點，接回時就對不上。

1. 讀每個 `Spec/Deferred/*.md` 檔末接回清單。
2. 草案要改寫／刪除的條文若含某列錨點 → 歸**弱連動**，註明「會讓 <功能> 更難接回」，PM 選項：**A** 同批更新該列原句與錨點（spec-writer 做）／**B** 接受，接回時 PM 手動對／**C** 改草案避開。
3. 草案內容與延後功能本身矛盾 → 同樣歸弱連動，提醒 PM 接回時要重議。

寫入後的第二道：`@phase0-spec-verifier` 維度 4 逐列驗錨點仍在。

## Scanner 的職責邊界

| 項目 | Scanner | Spec-writer |
|---|---|---|
| 讀整份 SPEC | ✅ | 只讀要改的檔案 |
| 找連動點 | ✅ | ❌（直接信任 PM 拍板後的清單） |
| 列出原文摘要 + 為什麼相關 | ✅ | ❌ |
| 產出「建議的修改文字」 | ❌（不做，避免越權） | ✅ |
| 實際改檔案 | ❌ | ✅（寫 .md source of truth，docx 由專案的 md→docx 轉檔工具反向生成，若有；工具未包含於此 repo） |
| 替 PM 做選擇 | ❌ | ❌ |
| 拒絕格式不完整的輸入 | ✅ | ✅ |

**底線：** Scanner 只指出「哪裡可能要改、為什麼」。怎麼改是 PM ↔ Opus 在 ⑥ 拍板階段的事。

## 觸發方式

| 方式 | 情境 |
|---|---|
| Opus 在草案明確後**主動呼叫** | 預設流程，Opus 判斷「草案夠成熟、可以掃描」時觸發 |
| PM 用 `@phase0-impact-scanner` **強制指定** | PM 想在任何時機手動跑一次掃描 |

兩種都應支援。

| 項目 | 由誰處理 |
|---|---|
| 從討論文字推敲出草案 | Opus 在 ③ 階段做 |
| 判斷哪些連動「值得改」 | PM 在 ⑥ 拍板時做 |
| 實際寫入 SPEC md | @phase0-spec-writer 在 ⑨ 做 |
| 更新 Project_Context.md / Decision_Principles.md | @phase0-spec-writer 在 ⑨ 做 |
| 寫 memory / 更新 README | @phase0-spec-writer 在 ⑨ 做 |
| 掃描 HTML 設計稿 | 不在 Phase 0 範圍，Phase 1 處理 |

## Checklist（Scanner 執行完前自檢）

> 本表合併自檢項、禁止行為與常見錯誤，一表為準；任一項不過即修正後再交。

| # | 檢查項（gate） | 防的錯（後果） |
|---|---|---|
| 1 | 輸入清單格式完整（議題編號、決策清單、關鍵詞）；不完整就拒絕執行，**不自己推敲草案** | 越過 Opus 推理層，錯誤理解議題 |
| 2 | 已掃所有必掃範圍（`Spec/*.md`、`討論排程/` 已定案、CLAUDE.md 必讀背景文件） | 漏掃＝連動風險漏網 |
| 3 | 未掃禁區（History/、HTML設計稿/、未定案議題、`Spec/*.docx`）——掃描前先 Glob 過濾 | 過時 / 未拍板內容污染結果，違反 CLAUDE.md 紅線 |
| 4 | 三層分類無重疊（一條條文只屬一層）；弱連動必須指向**具體現有條文**，不收「未來可能擴充」猜測 | PM 看到一堆雜訊，失去訊號 |
| 5 | 強連動每項含「原文摘要＋衝突點＋建議處理方向」；弱連動每項含「原文摘要＋關聯點＋PM 判斷選項」 | 沒原文摘要，PM 無從判斷 |
| 6 | 只給「建議處理方向」，**不寫具體修改文字、不替 PM 做選擇** | 越權，與 spec-writer 責任重疊 |
| 7 | 無影響層列出已掃檔案清單；末尾宣告「已掃 / 跳過 / 掃描檔案總數」 | PM 不知道是否漏掃 |
| 8 | **章節編號完整性順掃**：對目標 SPEC 跑 H1/H2/H3 grep（照 `SPEC_NUMBERING_RULES.md` §六），破損列入「【既有編號問題】補充提示」段 | 編號債務無人記錄，寫入時才炸 |
| 9 | **crosscheck 八面向已順掃**（術語 / API / 權限 / 狀態機 / 跨 SPEC / 彙總層 / 同列同表全列重讀 / 死路檢查），不一致項已歸入強 / 弱連動 | 一致性缺口漏網 |
| 10 | **接回錨點已比對**：`Spec/Deferred/*.md` 每列錨點對草案改寫範圍；命中者已列弱連動並註明「更難接回」（無 Deferred 檔 → 註明跳過） | 延後功能悄悄接不回去 |
