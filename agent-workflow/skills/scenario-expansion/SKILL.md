# 🧭 情境展開（Scenario Expansion）

**一句話心法**：前面的情境矩陣＝後面的測試矩陣——把「列 test case」提早到設計之前做。

> 範例一律用虛構的「待辦清單 App」（任務、清單、被指派者、到期日、提醒、共享）。換專案時把例子換成自己的 domain，結構照用。

## 0｜何時用、接在哪

```
[需求一句話]
   ↓  ← 本 skill 在這裡跑
情境矩陣（§6 輸出）
   ↓
phase1-product-designer   ← 矩陣告訴它要畫哪些「狀態」
   ↓ 同時
phase4-test-writer        ← 矩陣直接變 test case
   ↓
phase0-mockup-drift-scanner ← 收尾掃覆蓋缺口
```

跑法：把功能/改動描述丟進來 → 依序跑 §1～§5 的展開動作 → 產出 §6 矩陣 → 才進 phase1。**寧可在這裡多花 15 分鐘，不要在 phase6 才發現漏一個狀態。**

---

## 1｜通用狀態軸（每個畫面/流程都掃一遍）

對「畫面」與「動作」各問一輪。漏了哪一格 = 之後一定補單。

**畫面狀態軸**
- 資料量：**空（0 筆）** / 1 筆 / 正常 / **爆量（要分頁？虛擬捲動？）** / 超長字串截斷
- 載入：loading 骨架 / 部分載入 / **timeout / 失敗重試**
- 權限：有權限（完整）/ 唯讀 / **無權限（隱藏 vs 灰掉 vs 403 頁）**
- 時間：第一次使用（空狀態引導）/ 重複使用 / 資料已過期

**動作狀態軸**
- 正常成功
- 驗證失敗（欄位級錯誤訊息長怎樣？）
- 後端失敗（API 500 / 網路斷）
- **併發衝突**（兩人同時改同一筆 → 後寫覆蓋？樂觀鎖？）
- 重複提交（連點兩次 / 重整後再送）
- 取消 / 中途離開（未存資料怎麼辦）

---

## 2｜每條需求展開 HP / EC / ER

對需求裡**每一個動作**強制寫滿三欄，不准只寫 HP（HP＝Happy Path 主流程、EC＝Edge Case 邊界情境、ER＝Error 錯誤／例外情境，與 [`workflow/phase-4-tests.md`](../../workflow/phase-4-tests.md) 的 test_id 分類同義）：

| 動作 | HP | EC | ER |
|---|---|---|---|
| （例）清單擁有者批次改任務到期日 | 全部任務可改、套用成功 | 部分任務已完成、有任務設了重複規則、有任務已有人改過到期日 | 清單已被刪、權限不足、套用一半失敗的回滾 |

> EC 想不到時 → 回去 §1 的軸逐格套；還想不到 → 進 §4 domain 軸（漏點幾乎都在那）。

---

## 3｜把情境寫成 User Story 並過 INVEST

每條情境收斂成一句（對齊 phase1 的 product-spec.md User Story 格式）：

> 身為 **<角色>**，我要 **<做什麼>**，以便 **<得到什麼價值>**。
> 驗收：Given **<前提>** / When **<動作>** / Then **<結果>**。

**INVEST 自檢**（任何一項 No 就拆小或補資料）：
- **I**ndependent 能獨立交付？ · **N**egotiable 還有討論空間？ · **V**aluable 對使用者有價值？
- **E**stimable 估得出工？ · **S**mall 夠小？ · **T**estable **能被 phase4 寫成測試嗎？**（最重要）

> 需要正式 PRD 的大功能，才另開 8 段式（背景 / 目標 / User Stories+驗收 / 功能需求 / 非目標 / 技術考量 / 成功指標 / 待解問題）；一般功能直接走「情境矩陣 → phase1」即可，不要為了形式多開一份會跟 Phase 0–8 打架的文件。

---

## 4｜🔴 DOMAIN 軸 — 共用盲點清單

> 專案有自己的 domain 盲點清單（建議放在專案 `Spec/` 下，欄位分「情境層問」與「任務層問」）就用它；沒有就用下表起步，踩過的雷再補進專案清單。
> 逐軸看「**情境層問**」欄展開，每軸記一句「牽涉／不牽涉」。

| 軸 | 情境層問（以待辦清單 App 為例） |
|---|---|
| 角色 × 權限 | 擁有者（Owner）／編輯者（Collaborator）／唯讀成員（Viewer）／被指派者各看到什麼、能做什麼？同一人身兼兩種角色時規則看哪個？ |
| 狀態機 | 任務的每個狀態（草稿、待辦、進行中、完成、封存）之間哪些轉換合法？倒退（完成→待辦）允許嗎？ |
| 時間與排程 | 到期日跨時區、跨日界線、夏令時間怎麼算？重複任務的下一期怎麼生？提醒時間早於現在呢？ |
| 成員與擁有權異動 | 做到一半，被指派者被移出清單、帳號被刪，或清單擁有者轉移，各會怎樣？ |
| 既有資料感知 | 設定改了之後，已經存在的任務要套新規則還是保留舊值？使用者自訂過的值要不要蓋掉？ |
| 數量與空狀態 | 0 筆 / 1 筆 / 大量；批次操作混合不同狀態時怎麼處理？ |
| 併發 | 兩人同時編輯同一任務、同時勾完成、一人刪清單時另一人正在新增任務？ |
| 通知 fan-out | 誰會收到（擁有者、被指派者、所有成員）？自己做的動作要不要通知自己？什麼情況不該寄？ |
| 刪除與資料保留 | 刪掉的任務／清單是軟刪還是真刪？能復原嗎？其他規則（統計、提醒）還會用到它嗎？ |
| 文案與錯誤 UI | 空狀態、錯誤訊息、確認對話框的字句寫了嗎？多語系都寫了嗎？ |

> 逐軸掃完，**接著跑 §4.5 的「Phase 0 邊界 12 問」**——那 12 題是 domain 軸的固定提問版，漏答哪一題之後就會變補單。

---

## 4.5｜🧭 Phase 0 邊界 12 問（scope gate 候選欄的固定來源）

> 出處：把過去規格上線後才補洞的案例歸成 12 型，一型一問。
> §4 逐軸掃的是「這次牽涉到什麼」；這 12 題掃的是「**歷史上都在這 12 個地方漏**」——兩者互補，都要跑。

### 規則（不准跳題）

- **每題必答其一**，不得空白：
  - `有情境` → 把情境**列出來**（幾條就寫幾條，進下面的候選欄）
  - `確認不適用` → 寫**一句理由**（例：「本次不動通知，提醒信規則不受影響」）
- 「想不到」不是答案；想不到就回 §4 對應軸的「情境層問」欄逐格套。
- 12 題答完才產候選欄；**候選欄不得只列主流程 Claude 自己想到的**（見 [`workflow/phase-0-spec-update.md`](../../workflow/phase-0-spec-update.md)「✋ 寫前範圍控管」）。

### 12 題

| 題 | 問題 | 對應軸 |
|---|---|---|
| Q1 | 這功能產生的每個提醒 / 徽章 / 待處理標記：清單封存、任務變唯讀之後，當事人還做得到「讓它消失」的那個動作嗎？做不到的話那個標記怎樣？ | 死路 / 規則打架 |
| Q2 | 把中間狀態一個一個叫出名字（開了沒存 / 存了沒分享 / 清單建了沒成員 / 任務沒到期日）：每個狀態下各角色看到什麼、能做什麼？ | 狀態機 |
| Q3 | 到期日比提醒提前量還近會怎樣？跨時區、跨日界線算哪一天？重複任務從上一期複製日期會怎樣？ | 時間與排程 |
| Q4 | 同一人同時是清單擁有者又是被指派者會怎樣？規則看「從哪個入口進來」還是看「他是誰」？ | 角色 × 權限 |
| Q5 | 做到一半，清單擁有者轉移、被指派者被移出清單、帳號被停用或刪除、共享被撤回——各會怎樣？ | 成員與擁有權異動 |
| Q6 | 擁有者在大家已經用過、自訂過之後才改這個設定，既有資料怎麼辦？要通知誰？ | 既有資料感知 |
| Q7 | 0 筆 / 剛好 1 筆 / 2+ 各會怎樣？一批混合兩種狀態呢？畫面寫「影響 N 筆」的 N 到底算什麼？ | 數量與空狀態 |
| Q8 | 這則通知寄給誰、含哪些成員？步驟順序顛倒（任務先完成、之後才被指派）會怎樣？什麼情況不該寄？ | 通知 fan-out |
| Q9 | 這條規則還寫在哪些章節 / Glossary / 權限表 / 通知文案 / mockup？全部都改了嗎？ | 下游漂移（→ phase0-impact-scanner） |
| Q10 | 每顆按鈕什麼時候可按、什麼時候灰掉——單筆一套、批次一套，都寫了嗎？ | 按鈕啟用／禁用 |
| Q11 | 文案實際字句各語言都寫了嗎？在每個狀態、每個看得到它的角色眼裡還說得通嗎？ | 文案與錯誤 UI |
| Q12 | 資料刪掉之後是真的消失嗎？後面還有沒有哪條規則要用到它的值？ | 刪除與資料保留 |

### 輸出：scope gate 的 `候選衍生情境` 欄

12 題答完，把所有 `有情境` 的條目攤成下表（就是 `workflow/phase-0-spec-update.md` scope gate 草案右欄的內容）。**每條標【建議寫 / 建議跳過】＋一句理由，預設從嚴、偏少；勾哪些由 PM 決定，主流程 Claude 不自己加戲。**

| 來自第幾題 | 候選情境（一句話） | 建議 | 一句理由 |
|---|---|---|---|
| Q1 | （例）清單封存後，逾期徽章無法清除 | 【建議寫】 | 使用者會卡死、無路可走 |
| Q7 | （例）批次改到期日時混合「未完成 / 已完成」任務 | 【建議寫】 | 前端已在猜要不要跳過已完成，不寫就是工程端補空白 |
| Q11 | （例）提示文案的英文版 | 【建議跳過】 | 本次不上英文介面，留到 i18n 批次 |

不適用的題目也留一行痕跡（`Q3 確認不適用：本次不動任何日期欄位`），**留痕的目的是之後不會再有人說「當初沒想到」**。

## 5｜假設攤開 → 接 Phase 2.5 PENDING

把這次需求**隱含的假設**全列出來，逐條標記：

| 假設 | 狀態 | 暫定值（給 phase5 不卡） |
|---|---|---|
| （例）重複任務改到期日時只改這一期 | `待 PM 拍板` | 先只改這一期 |
| （例）唯讀成員看不到他人的私人備註 | `已確認` | — |
| （例）逾期提醒文案 | `待需求方確認` | mock 文案 |

狀態三類：`已確認` / `待 PM 拍板` / `待需求方確認`。後兩類直接餵進 `dev-spec/PENDING_SPEC.md`（P0/P1/P2 分層），開發不被阻擋。

## 6｜輸出：情境矩陣（餵 phase1 + phase4）

最終吐這張表。**每一列**之後就是 phase1 要畫的一個狀態、phase4 要寫的一個 test case：

| 序 | 情境 | 角色 | 觸發/前提 | 預期行為（Then） | 優先級 | 給 phase1（畫面狀態） | 給 phase4（test 標題） |
|---|---|---|---|---|---|---|---|
| 1 | 正常批次改到期日 | 清單擁有者 | 清單存在、任務皆未完成 | 套用成功、顯示成功 toast | P0 | 成功態 | `擁有者批次改到期日成功` |
| 2 | 任務已被他人改過到期日 | 清單擁有者 | 編輯者剛改過其中一筆 | 提示衝突、讓使用者選覆蓋或保留 | P0 | 衝突確認 modal | `批次改到期日_遇他人修改提示衝突` |
| 3 | 無權限 | 唯讀成員 | 非擁有者／編輯者 | 動作隱藏 / 403 | P1 | 無權限態 | `唯讀成員_無法批次改到期日` |
| … | | | | | | | |

> 優先級判準見 [`workflow/phase-1-product-design.md`](../../workflow/phase-1-product-design.md)「升 AC 判準」。

**收斂檢查**（全 Yes 才放行進 phase1）：
- [ ] §1 通用軸每格都問過，空/ER/權限/併發都有對應列
- [ ] §4 domain 各軸逐條確認「牽涉/不牽涉」（不牽涉也要記一句）
- [ ] 每條 User Story 過 INVEST 的 **T（可測）**
- [ ] §5 假設全標狀態，待拍板的進了 PENDING
- [ ] 矩陣每列都填了「給 phase4」欄 —— 這欄空 = 這情境之後沒人驗

## 7｜與 Phase 0–8 的銜接

| 本 skill 產出 | 流向 |
|---|---|
| 情境矩陣（§6） | → `phase1-product-designer`：要畫的狀態清單；標的 `data-spec` 來源 |
| 矩陣「給 phase4」欄 | → `phase4-test-writer`：直接變 AGENT_TEST_INSTRUCTION 的 case |
| 假設表（§5） | → `phase25-pending-manager`：P0/P1/P2 暫定值 |
| domain 軸命中的條文 | → `phase0-impact-scanner`：預判會連動到哪些既有定案 |
| §4.5 候選衍生情境欄 | → Phase 0 scope gate（[`/spec-change`](../../commands/spec-change.md) Step 4） |

> 本 skill **不取代** phase1，它是 phase1 的**前置盤點**。phase1 仍照常產 annotated mockup + product-spec.md，只是這次它手上已經有一張不漏的情境矩陣。
