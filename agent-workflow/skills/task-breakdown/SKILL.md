# ✅ 任務拆解（Task Breakdown）

類似「writing-plans」，但**對話式 + PM 級**。輸入是「功能一句話 + 範圍」，輸出是「帶完成定義的 to-do 清單」。

> 管線位置見 [`workflow/entry-routing.md`](../../workflow/entry-routing.md)。範例用虛構的「待辦清單 App」。

## 0｜硬規則：放對高度

- ❌ 不要產出 code 檔案路徑、不要寫「每行怎麼測」「改哪個 function」——那會變成工程版計畫，且踩進 phase2/phase5 的地盤。
- ✅ 只到**任務級**：每個 to-do 配一句 **DoD（怎麼算做完）**。這句之後直接長成 scenario-expansion 的情境、phase4 的 test case —— 驗證往前種，但種在「任務」高度。

## 1｜輸入（PM 給這兩行就能開始）

- **功能一句話**：這次要做什麼
- **範圍**：做什麼（in）／**不做什麼（out）** —— out 一定要寫，這是擋範圍蔓延的關鍵

範圍講不清就先退回 `brainstorming`，別急著拆。

## 2｜對話式拆解（像 brainstorming，不要一次吐完）

1. 先丟**一版拆法草稿**（5–9 個 to-do，太多代表範圍該再切）
2. PM 增 / 刪 / 合併 / 改範圍
3. 收斂定版

拆的時候主動逼問，而不是等 PM 想：
- 「這個範圍邊界對嗎？這塊要不要切出去當另一個功能？」
- 「**有沒有漏掉一整類工作？**」←（見 §4 常漏清單）
- 「哪幾個 to-do 之間有相依、誰要先做？」

## 3｜每個 to-do 的格式

| 欄位 | 說明 |
|---|---|
| **標題** | 動詞開頭、垂直切片（能獨立交付一小塊價值，不是「寫 DB / 寫 API / 寫前端」這種水平層） |
| **DoD** | 一句「怎麼算做完」——**寫成可驗證敘述**（可被觀察 / 可被測；避免「系統正確處理」這種測不到的話） |
| **In/Out** | 屬於這個 to-do 的、明確不屬於的 |
| **相依** | 要先做完哪個 to-do |
| **優先級** | P0 / P1 / P2 |
| **不確定** | 標 `待 PM 拍板 / 待需求方確認` → 進 PENDING，不卡拆解 |

> 切法原則：**垂直優先**。「被指派者能在『我的任務』看到指派給自己的任務」是好 to-do；「建任務指派 table」不是（它只是某個 to-do 的一部分，且無法獨立驗收）。

## 4｜🔴 常被漏掉的任務類型（拆完一定回頭對一遍）

> 專案有自己的 domain 盲點清單就看它的「**任務層問**」欄；沒有就用下表起步。逐條問「這次需不需要？需要就補一個 to-do」。

| 類型 | 任務層問（以待辦清單 App 為例） |
|---|---|
| 權限 | 權限表要不要加一列？唯讀成員、被移出的成員碰到這功能時的行為有 to-do 嗎？ |
| 既有資料 | 上線前已存在的任務／清單要不要遷移或補預設值？ |
| 通知 | 要不要新增或改通知（站內、信件、推播）？文案與收件人有人負責嗎？ |
| 時間 | 牽涉到期日／提醒時，時區與重複任務的處理有 to-do 嗎？ |
| 刪除與復原 | 刪除要不要可復原？連帶影響（提醒、統計）有人收嗎？ |
| 批次操作 | 單筆做得到的，要不要也支援批次？批次的部分失敗怎麼回報？ |
| 空狀態與錯誤 UI | 空清單、載入失敗、無權限畫面有人畫嗎？ |
| 多語系 | 新文案要不要翻譯？ |
| 文件 | User Guide／說明頁要不要改？ |
| 下游同步 | Glossary、權限表、既有 mockup 會不會因此過時？ |

## 5｜輸出與交棒

最終吐一張 to-do 清單（§3 格式）。然後交棒：

| 本 skill 產出 | 流向 |
|---|---|
| to-do 清單 | → [`scenario-expansion`](../scenario-expansion/SKILL.md)：**逐條** to-do 展開情境矩陣 |
| 每個 to-do 的 DoD | → `phase4-test-writer`：變成驗收 test case（P0 級 DoD＝AC 子節雛形；升 AC 判準見 [`workflow/phase-1-product-design.md`](../../workflow/phase-1-product-design.md)） |
| 標「待拍板/待確認」的 to-do | → `phase25-pending-manager`：P0/P1/P2 暫定值 |
| 範圍 Out 清單 | → Phase 0 議題 / product-spec 的「非目標」 |

> 本 skill **不**決定怎麼實作、不畫 UI、不寫測試腳本——它只回答「這個功能要做哪幾件事、每件怎麼算做完」。後面交給 Phase 0–8。
